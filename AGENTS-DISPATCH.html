Agents 外派能力（P1 + P2 后端契约） ​

面向：P3 前端（已按本文契约实现）、验收方、后续接手的人。 代码：packages/agent/src/acp-client.ts、packages/agent/src/agent-task-store.ts、 packages/server/src/agent-runtimes.ts、packages/server/src/agent-task-service.ts、 packages/server/src/routes/agent-tasks.ts、packages/tools/src/builtin/dispatch-task.ts。

1. 能力边界 ​

  • 能做什么：把一条任务派给本机另一个 ACP agent（kimi / dsh / fengagent …），拿回最终 回复；界面能看到 runtime 卡片、任务 7 态、事件时间线与流式输出。
  • 不做什么（本阶段刻意不做）：跨机调度、常驻进程池、自动重试、拓扑图、Schedules。
  • 目标 agent 的凭据由它自己管；本仓库只负责拉起进程 + 说 ACP。

2. 任务状态机（7 态，与 web-ui/src/api/types.ts 同枚举） ​

状态进入条件允许去向
created建任务成功（幂等键可复用既有任务）dispatched / cancelled / expired / failed
dispatched已 spawn 目标进程并落 task/dispatchedrunning / replied / failed / cancelled / expired
running已 session/new 成功（accepted 事件之后）replied / failed / cancelled
repliedprompt 正常结束，结果已落库终态
failed目标报错 / 超时 / 未注册 / 台账未决终态（可 retry）
cancelled用户取消（session/cancel + 关客户端）终态（可 retry）
expired服务重启时该任务还没派发出去终态（可 retry）

dispatched → replied 是允许的：目标可能一句话不说就结束（无增量输出）。

事件枚举（agent_task_events.type，与前端 AgentTaskEvent["type"] 一致）： task/created、task/dispatched、task/accepted、task/running、task/stream-chunk、 task/replied、task/failed、task/cancelled、task/expired、task/retried。

seq 每个任务内单调递增（1 起），事件流可重放出当前状态 （AgentTaskStore.replayStatus() / replayAgentTaskStatus()）。

统一错误体：runtime 管理面（上表前 8 行）失败一律回 { "error": { "message": "…", "code": "…" } }，message 是可以直接展示给人看的 具体原因，code 是分类：

任务字段（AgentTask）：id, fromSession, runtime, status, content, result?, error?, createdAt, dispatchedAt?, startedAt?, finishedAt?, durationMs?, acpSessionId?（时间是 ISO 字符串）。

语义约定：

  • 幂等键：idempotencyKey 在存储层建唯一索引；重复 POST 返回同一任务（200/201 都返回该任务， 不会再派一次）。这是「用户手抖点两下」的闸。
  • retry 语义：同 taskId 的新 attempt（attempt+1），事件流里有一条 task/retried （detail 记录上一状态）。不自动重试 —— 每次重试都必须显式发生。
  • 目标会话复用（session/resume）：任务第一次派发走 session/new，acpSessionId 记在任务上； retry 时若握手声明了 resume 能力，就带全参 {sessionId, cwd, mcpServers} 续聊同一个目标会话 （cwd 不能省：kimi / 原版 dsh 会强制校验）。resume 失败（目标不支持 / 会话已被回收）自动回退 session/new，原因写进 task/accepted 的 detail，派发不因此失败。
  • expired：只在服务重启时把「还没派发出去的 created 任务」转入，没有定时 TTL。
  • headless 权限：目标 agent 发 session/request_permission 时，策略默认 deny，决策写进 事件流（task/stream-chunk + [permission] <tool> → allow|deny）。冻结的事件枚举没有独立类型， 这里复用 detail 承载，UI 时间线可见，绝不静默挂起。 回给目标的 optionId 按目标实际提供的选项挑（kind 优先：allow_once / approve_once / accept_once…；再按 id 字面量兜底；没有 options 才回退 allow-once）—— kimi 用 approve_once/approve_always/reject，dsh 系用 allow-once/reject-once，硬编码会让 kimi 的 allow 失效。

4. SSE（GET /api/agent-tasks/:id/stream） ​

帧类型（AgentTaskStreamEvent）：

jsonc
{"type":"status","task":{...}}            // 快照 / 状态变更
{"type":"chunk","text":"增量文本"}          // 流式输出（不落库）
{"type":"event","event":{"seq":7,...}}     // 持久事件（带 id: <seq>）

连接顺序：快照 → ?after=<seq> 之后的历史事件 → 实时帧；终态帧发出后服务端主动结束。 重连用 ?after=<seq>（或 Last-Event-ID）只补发缺的事件，不重复渲染。 心跳每 15s 一条注释帧（: heartbeat）。

每次状态转移都推两帧，顺序固定：先 event（task/<status>），再 status。 终态也一样 —— 服务端收到终态 status 帧就结束流，所以 task/replied / task/failed / task/cancelled 事件帧一定在终态 status 之前发出（F 段 P0 修复）。客户端只看 event 帧就能重建完整时间线，status 帧只负责驱动状态徽标。

4.5 身份隔离（子进程环境与工作目录） ​

派发出去的目标 agent 是独立进程，不该继承我们这侧的身份：

  • 环境变量：只透传系统必需的白名单（PATH / SystemRoot / TEMP / USERPROFILE 等， 见 buildAcpChildEnv()），不含 MULTICA_*（尤其 task token）与调用方 provider key。 目标真需要凭据，在 <数据根>/runtimes.json 的 env 里显式给，或让它读自己的配置文件。
  • 工作目录：默认 ~/.fengagent/dispatch-workspace/<数据根指纹>（仓库外）。 放在仓库里会让目标读到 AGENTS.md / CLAUDE.md / .git，从而自称成别的 agent、 或把这次外派当成在自己项目里干活（F 段 P0）。POST /api/agent-tasks 的 cwd 可显式覆盖，但默认值保证中立。

5. 不重复执行（副作用台账） ​

每次派发是一个副作用操作：operationKey = agent-task:<taskId>:attempt-<n>， 写 AGE-29 的 operation_ledger（OperationLedger，与 Agent Loop 共用同一套）：

台账状态派发行为
无记录正常执行（begin → complete/fail）
succeeded不重跑，直接把 result_json.text 回放成结果（补一条 task/dispatched 再 replied）
pending / unknown拒绝重跑，任务落 failed：副作用未决…需人工核对后再 retry
failed允许重新执行（begin 会把 failed 重置为 pending）

6. 崩溃恢复语义 ​

服务启动时 recoverInterrupted()：

  • created（从未派发）→ expired；
  • dispatched / running → failed（detail：服务重启中断，未自动重跑，可 retry）。

不自动重跑是刻意的：远端可能已经执行过，自动重跑会破坏「副作用次数 ≤ attempt 数」。 重启后 UI 看到的状态与事件流都由 SQLite 重放而来，seq 连续。

7. 运行时注册表（<数据根>/runtimes.json） ​

json
{
  "runtimes": [
    { "name": "fengagent", "command": "fengagent", "args": ["acp"], "enabled": true },
    { "name": "dsh", "command": "dsh-acp", "args": ["acp"], "enabled": true },
    { "name": "kimi", "command": "kimi", "args": ["acp"], "enabled": true },
    { "name": "fake-allow", "command": "kimi", "args": ["acp"], "enabled": true,
      "permissionPolicy": "allow", "env": { "SOME_KEY": "值" } }
  ],
  "probes": { "kimi": { "status": "ok", "agentName": "Kimi Code CLI", "agentVersion": "0.34.0", "probedAt": "…" } }
}
  • 缺文件时自动写默认三件套；probes 是探测结果缓存（启动时后台探一次，也可 POST /api/runtimes/probe 手动刷新）。
  • 探测 = spawn 目标 + initialize + 立刻回收（超时 20s，dsh 冷启实测 ~13s）。
  • 加一个 runtime 只改这个 json，不改代码 —— 页面上「添加 runtime」走的也是这一条 （POST /api/runtimes，见 §7.1）。
  • permissionPolicy（可选，"allow" / "deny"）：该 runtime 的 headless 权限策略， 覆盖服务默认的 deny。验收需要目标真写文件（marker 类）时，给测试 runtime 配 "allow"； 决策仍会写进事件流（[permission] … → allow|deny）。
  • env（可选）：显式注入目标进程的环境变量 —— 这是往目标传凭据的唯一推荐方式 （默认不透传调用方的 MULTICA_*，见 §4.5）。

7.1 增删改 + 探测验证（/api/runtimes 写接口） ​

团队页「成员库」的添加/编辑/删除与「探测验证」按钮都落在这里，失败必须带具体原因：

  • 新增：name 必填且要能当派发参数（^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$）、command 必填并 当场在 PATH 里解析（找不到直接 command_not_found，不等 20s 探测）、protocol 缺省 acp。 probe=true 时先真 spawn 一次 initialize：失败 → 422 + 原因，不落盘（不留下永远派不出去的注册）。

  • 协议闸（重点）：dispatch 只实现了 acp 与 claude-stream-json。其它值一律 unsupported_protocol，并且对认识的命令直接点名它的原生协议：

    填的 command填的 protocol结果
    opencodeacp400 协议不支持: opencode 的 run --json（一次性事件流），不是 acp…
    opencoderun-json400 协议不支持: … dispatch 目前只实现 acp 与 claude-stream-json
    claudeacp400 提示应选 claude-stream-json
    kimiacp通过（真探测才知道可不可达）

    这条刻意不做「按 ACP 硬 spawn 试试看」：opencode 的 run --json 不是 JSON-RPC，硬试只会得到 一串看不懂的握手错误 —— 而「协议不支持」才是人能行动的答案。

  • 编辑：PATCH 只覆盖 body 里出现的字段；注册名（= dispatch_task 的 agent 参数）不可改； 改了 command/args/protocol/env 后旧探测结果作废（回到 unprobed），避免卡片显示过期「可用」。

  • 删除：直接删条目 + 清探测缓存（历史任务不受影响，仍可查）。

  • 探测验证（表单）：POST /api/runtimes/probe-candidate 不落盘、不抛错，永远回 {probeStatus, probeError?, probeErrorCode?, agentName?, agentVersion?, capabilities?}， 前端把 probeError 原样显示。

  • 探测失败归类：credentials_missing（目标自报缺 key / 未登录）、handshake_failed（不是所选协议， 带 stderr 尾巴）、spawn_failed（EINVAL/EACCES）、command_not_found、probe_timeout。 RuntimeInfo 上同时给 probeError（人话）与 probeErrorCode（分类）。

8. dispatch_task 工具 ​

会话里的 LLM 可以直接调用：

jsonc
{ "agent": "kimi", "task": "自包含的任务文本", "cwd": "可选" }
  • 走 AgentTaskService.dispatchAndWait()：建任务 → 派发 → 等终态 → 把回复文本作为工具结果返回； 因此「结果回流到当前会话」不需要额外机制。
  • fromSession 自动填当前会话 id（Agents 页的 From 列因此能显示来源）。
  • 工具声明 sideEffect: non-idempotent：它自己也进副作用台账（崩溃后未决的派发不会被静默重放）。
  • 仅在 server 装配（createRuntimeAgent）里注册 —— enableSessionStore=false 或服务初始化失败时不可用。

9. 与方案的两处有意偏离（已在代码注释里写明） ​

  1. 没有把 7 态塞进 TaskStore.task_states：那张表的状态机服务于 Agent Loop（步级 checkpoint / 待结算工具），枚举是 active/blocked/completed/aborted。硬塞会污染已验收的 loop reducer。 改用同构的事件溯源表 agent_tasks + agent_task_events（seq 单调 + 可重放）， 并复用 operation_ledger 做防重复执行 —— 机制相同，语义不混。
  2. 权限决策复用 task/stream-chunk 事件承载（[permission] 前缀）：冻结的事件枚举里没有 独立类型，为了不破坏 P3 的类型契约，用 detail 表达，UI 时间线可见。

9. 协议适配（P4 首块：claude stream-json） ​

外派执行面按注册表的 protocol 选择驱动，任务仓 / 7 态 / 事件流 / 台账完全复用：

protocol客户端进程模型会话权限
acp（默认）AcpClient长驻，session/new + session/promptsession/new / session/resume（全参）逐次 session/request_permission
claude-stream-jsonClaudeStreamJsonClient进程-per-prompt（claude -p）--session-id <uuid> 新建 / --resume <id> 续聊每次运行合成一次审批 → allow 加 --dangerously-skip-permissions
  • 门面：RuntimeDriver（packages/agent/src/runtime-driver.ts）。两种客户端保持同构表面 （initialize / newSession / resumeSession / prompt / cancel / close）， ClientRuntimeDriver 把「能 resume 就 resume、失败回退 new」与「文本增量提取」收在一处； 服务层只跟 RuntimeDriver 打交道，加一种协议 = 加一个同构客户端。
  • claude 的差异都在客户端里消化：--version 短命探测当握手（不产生模型调用）、 prompt 走 stdin（避免 Windows 命令行长度限制）、事件 assistant 文本块 → onUpdate、 result 事件即终局（is_error → 抛错）、session_id 跑完才出现 → 服务在 replied 前用 setAcpSessionId() 补记，供下次 retry 续聊。
  • 注册表加一条即可用（默认已内置）：
json
{ "name": "claude", "command": "claude", "protocol": "claude-stream-json",
  "enabled": true, "permissionPolicy": "allow" }
  • v1 限制：claude 只有块级文本增量（assistant 消息块，不是逐 token）；没有交互式审批 （headless 一次性决策）；同一客户端实例一次只能跑一轮（服务本来就是「一任务一驱动」）。
