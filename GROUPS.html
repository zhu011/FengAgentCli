群聊（G1 后端：契约冻结 v1.0 实现说明） ​

契约来源：issue 里 KG 冻结的 G1 API 契约 v1.0（web-ui/src/api/types.ts 群聊段与之同形）。 实现：packages/agent/src/agent-group-store.ts、packages/server/src/agent-group-service.ts、 packages/server/src/routes/groups.ts、packages/tools/src/builtin/group-tools.ts。

1. 模型：对话聚合 vs 生命周期聚合 ​

表角色关键字段
agent_groups群（对话聚合根）id(grp_…) / name / description / `status(open
group_messages群聊日志（append-only）id(msg_…) / seq（群内单调，1 起） / from_kind / from_name / content / kind / agent_task_id
  • 任务不进群表：群内派发复用 agent_tasks（G2 加 groupId 语义），群消息只用 agentTaskId 反指任务 —— 7 态状态机不受影响。
  • members_json 存成员（runtime + 协调者），对外 members = runtime 名列表（人隐含在场， 不占位；协调者 fengagent 会出现在列表里）。
  • kind：chat（G1 默认）/ task_card（G2）/ decision（G3）/ system（建群等系统提示）。

2. HTTP API（与契约逐条对齐） ​

方法路径请求响应
GET/api/groupsstatus / limit（可选）{groups: GroupInfo[], runtimes: RuntimeInfo[]}
POST/api/groups{name, description?, members: string[], maxRounds?, speechMode?}201 GroupInfo；成员未注册/未启用 → 400
GET/api/groups/:id—{group, messages}（全量消息，G1 不分页）
POST/api/groups/:id/messages{content, kind?: "chat"}201 GroupMessage（fromKind=human、fromName=human）；已 concluded → 409
POST/api/groups/:id/agent-messages{content, fromName, kind?}201 GroupMessage（协调者 → coordinator，成员 runtime → runtime）；非成员 → 403；已关群 → 409
POST/api/groups/:id/conclude—GroupInfo（status=concluded，幂等：重复调用返回原样）
PATCH/api/groups/:id{name?, description?, members?, maxRounds?, speechMode?}GroupInfo（契约外的便利接口，改名/改成员/切模式用）
GET/api/groups/:id/messagesafter / limit（可选）{messages, nextSeq}（增量读取；SSE 重连同款语义）
GET/api/groups/:id/streamafter（可选，默认 0）群 SSE（见 §3）

错误体统一 { error: { message, code } }，code ∈ bad_request | forbidden | not_found | conflict， HTTP 状态 400 / 403 / 404 / 409。

DTO：

ts
GroupInfo   { id, name, description, members: string[], status: "open"|"concluded",
              maxRounds, speechMode: "coordinated"|"free", createdAt, updatedAt, lastMessageAt? }
GroupMessage{ id, groupId, seq, fromKind: "human"|"runtime"|"coordinator"|"system",
              fromName, content, kind: "chat"|"task_card"|"decision"|"system",
              agentTaskId?, createdAt }

建群时会自动落一条 system 消息「群已创建」（fromName="system"）。

3. 群 SSE ​

GET /api/groups/:id/stream?after=<seq>       # 也接受 Last-Event-ID
  • 首帧 snapshot：{type:"snapshot", group, messages:[after 之后的消息], lastSeq}（一次给全）；
  • 实时：{type:"message", message}（SSE id: <seq>，可 Last-Event-ID 去重）、 {type:"group", group}（conclude 等属性变更）；
  • 心跳：{type:"heartbeat"} 数据帧，15s 一条；
  • 群删除时结束流（G1 无删除接口，预留）。

4. 谁能发言（v1 协调者中转） ​

来源写入路径from_kind / from_name
人POST /:id/messageshuman / human
协调者（群内 fengagent）群工具 group_send → POST /:id/agent-messagescoordinator / fengagent
成员 runtime（G2 起）POST /:id/agent-messages（服务端装配调用）runtime / 成员 runtime 名
外部 runtime 的产出服务端代写：postRuntimeMessage()（G2 结果回群主路径，不开放 REST）runtime / runtime 名
系统postSystemMessage()system / system

外部 runtime 没有群工具（要注入 MCP，G4/v2）；它们的产出统一由服务端写进群并带 agentTaskId 深链 —— 不依赖成员自觉，也不会「某个 runtime 忘了发消息」。

5. 群工具（只注入本仓库 fengagent 侧，契约三个） ​

工具入参作用
group_create{name, description?, members?: string[]}建群（协调者 = FENG_GROUP_SELF_NAME，默认 fengagent）
group_send{groupId, content}以协调者身份发言 → coordinator
group_history{groupId, limit?}读最近 N 条（旧→新，#seq [from] content）

工具由 server 装配注入（createRuntimeAgent → createGroupTools(handler)），tools 包不 反向依赖 server。group_conclude / group_dispatch 属于 G3 / G2，本轮不放。

6. G2（已实现）：群内派发 + 结果回群 ​

  • 任务带群：POST /api/agent-tasks 与 dispatch_task 都接受 groupId；任务记录新增 group_id（老库自动 ALTER TABLE 补列 + 索引），任务 DTO 回显 groupId； GET /api/agent-tasks?groupId= 只列该群任务。
  • 结果回群（服务端代写）：任务终态时 AgentTaskService 通过下沉口 groupSink 调 postRuntimeMessage(groupId, {runtime, content, agentTaskId, kind:"task_card"})：
    • replied → 「任务 xxx（runtime）已完成：<结果>」（超 2000 字截断）；
    • failed → 「任务 xxx（runtime）失败：<错误>」（超 1500 字截断）；
    • cancelled → 「任务 xxx（runtime）已取消」。 消息 fromKind="runtime"、fromName=<runtime>、kind="task_card"、带 agentTaskId。 后端只保证 agentTaskId 这个锚点，跳转路由由前端决定（/agents?task=<id> 或 ?view=agents&task=<id> 都行）。群侧写失败只 warn，不影响任务已收尾的事实。
  • 提交即验群：submit() 带 groupId 时先用 groupSink.hasGroup() 校验，未知群直接 400（否则任务跑完才发现结果无处可回）。
  • 不带 groupId 的任务不回群（回归用例覆盖）。

7. G3（已实现）：编排收敛 + 人在环 ​

GroupOrchestrator（packages/groups/src/group-orchestrator.ts）三条独立策略，共用一个 幂等 conclude()：

策略触发行为
轮次上限 maxRounds同群内「自上次人类发言以来」协调者发言数达到上限自动收口（system 说明原因）；人类发言清零计数
静默超时 idleTimeoutMs群 open 且最后一条消息距今 ≥ 阈值（生产 5s 扫一次；测试手动 sweepIdle）自动收口
人类拍板human 发 kind:"decision" 的消息该消息落库后立即收口
  • 收口顺序：写 【收口】原因 的 system 消息 → 取消该群未终态任务（cancelledTasks， 有则再补一条「已取消 N 个在跑任务」）→ 群状态置 concluded。消息只能在 open 群写入， 所以顺序不能反。重复收口返回 concluded:false（幂等）。
  • 人类中途关停：POST /api/groups/:id/stop → {group, cancelledTasks}（关群 + 取消任务， 对应验收口径「关群后无残留任务」）。
  • POST /:id/conclude 在有编排器时也走同一条路径（留收口说明）。
  • group_conclude 工具（第 4 个群工具）：协调者把结论以 decision 消息落库 → 关群 → 报告取消任务数；返回 status + cancelledTasks。
  • decision 消息：kind="decision"，人类拍板与协调者结论都用它，前端可单独渲染。
  • HTTP 入口（G3 补）：
    • 人类拍板：POST /api/groups/:id/messages {content, kind:"decision"} → 201 并立即收口 （kind 白名单 chat | decision，其它值 400；task_card 只由服务端代写）。
    • 静默超时可配：POST /api/groups 与 PATCH /api/groups/:id 接受 idleTimeoutMs （默认 600000），GroupInfo 回显该字段供前端展示。

8. V2-3（已实现）：自治发言 —— speechMode / 发言预算 / @ 仲裁 / 轮数升级 ​

外部 agent 经 MCP 直连发言后，「谁说、何时说、何时停」从协调者调度变成域层策略。 落点在 @fengagent/groups（AgentGroupService + GroupOrchestrator），不新增调度进程：

speechMode语义
coordinated（缺省，v1 兼容）只有协调者调度回合；成员直连发言仍可用，但不计轮、不占预算、不参与仲裁（中途求助不改轮次模型）
free（自治）成员之间直接发言/求助，收敛靠下面四闸

free 模式四闸：

  1. 轮数升级：maxRounds 是总轮数，一轮 = 一名成员的一组连续发言（同一人连发不增轮， 换人才 +1）；人类发言把轮数清零。到上限自动收口（system 说明写明「free 模式共 N 轮」）。
  2. 发言预算：每成员每窗口最多 N 条（GroupOrchestratorOptions.speechBudget，默认 5 条 / 60s， 按成员分别计窗；协调者不计）。超预算的发言在落库前被拒： GroupError{code:"conflict"} → HTTP 409，消息不落库、不广播。
  3. 发言权仲裁：消息正文里 @某人（MCP 的 group_reply 同样只是发一条带 @ 的消息）→ 下一发言权归他；持权期间其他成员插话被拒（409）。人 / 协调者可随时发言（主持人改派）； 没人被 @ 时发言权开放。arbitration:"advisory" 只记录不拦截。 onTurn(groupId, speaker) 在发言权转移时回调，宿主可据此派发任务。
  4. idleTimeoutMs / 人类拍板不变（拍板即收口）。

实现要点：

  • 写前准入：AgentGroupService.onBeforeMessage(hook) 是新增的写前钩子 （onMessage 是写后观察，管不住刷屏）。GroupOrchestrator 构造时自动注册， free 模式下超额/抢权直接 409；钩子自身抛错按 fail-closed 处理。
  • 只拦「直接发言」：准入上下文带 source（human / agent / system / task-result）， 只有 agent（MCP、群工具、agent-messages）走预算与仲裁；服务端代写的任务结果 （postRuntimeMessage，task_card + agentTaskId）不占轮、不占预算、不改发言权，不会被 409 吞掉。
  • 状态可查询：orchestrator.getStatus(groupId) → {speechMode, status, maxRounds, rounds, coordinatorTurns, lastSpeaker?, nextSpeaker?, budget:{limit, windowMs, used, remaining}, idleTimeoutMs}，前端状态条（V2-4）直接用。
  • 持久化：agent_groups.speech_mode（老库自动 ALTER TABLE 补列，缺省 coordinated）； 便携 JSON store 同步补字段，老存档读成 coordinated。
  • 零回归：coordinated 下 onMessage 走 v1 原路径，准入恒放行；v1 用例全部保持通过。
